# THE ABSOLUTE RULEBOOK FOR DECLARATIVE SANDBOX JSON GENERATION
You MUST strictly evaluate against these rules. Any violation is a FATAL error resulting in rejection.

## Rule 1: Node Type & Port Dependency Constraints
- "base": The starting point. It dictates initial data generation. `ports.requires` MUST be strictly `[]`.
- "mutate" / "filter" / "trap": Intermediate processing or sabotaging steps. They MUST have BOTH `ports.requires` (consuming upstream data) and `ports.provides` (outputting new data).
- "export": The ending point. It saves the final data. It MUST have `ports.requires`, but `ports.provides` CAN be empty or contain `Deliverable:...` ports.
- "global": Global constraints (like final formatting). Both `requires` and `provides` can be `[]`.
- CRITICAL: Never force a node to be "base" if its intent clearly relies on upstream processed data.

## Rule 2: The Sandbox Role Exclusivity Rule (NEW)
- You MUST verify that a `sandbox_role` is explicitly assigned to EVERY node.
- It MUST be exactly one of: "Data_Generator", "Solver", or "Global_Constraint".
- "trap" and "base" nodes MUST ALWAYS be assigned "Data_Generator". "mutate" nodes MUST ALWAYS be assigned "Solver".

## Rule 3: The Data Profile & Schema Rule (OVERHAUL)
- The key `data_params` is STRICTLY FORBIDDEN. You must use `data_profile` instead.
- For "base" nodes, `data_profile` MUST contain `business_context`, `suggested_scale`, and `declarative_schemas`.
- `declarative_schemas` MUST be an object where values are ARRAYS OF STRINGS (Natural language descriptions of columns, e.g., ["Txn_ID", "City", "Revenue (Realistic distribution)"]).
- FATAL ERROR: It is STRICTLY FORBIDDEN to use legacy procedural fields such as `generator_type`, `kwargs`, `min`, `max`, or `port_to_column_mapping`. Reject immediately if these are present.

## Rule 4: Anti-Spoiler & Trap Integrity Rule
- ANTI-SPOILER: For "base" nodes, the schema MUST ONLY contain raw, unprocessed columns. DO NOT hallucinate columns that are supposed to be calculated or appended by downstream Solver steps (e.g., Do NOT include "Variance", "Sample_Flag", or "Is_Processed" in the base schema).
- TRAP INTEGRITY: For "trap" nodes, the `intents` MUST ONLY state the disruption or dirty data injection (e.g., "Inject null values"). It MUST NOT explain *how* the downstream model should fix or handle the trap.
